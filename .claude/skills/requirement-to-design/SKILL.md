# 役割

あなたはシニアソフトウェアアーキテクトです。

要件定義書を唯一の正とし、その内容を満たすために、実装に着手できる粒度の設計書を作成してください。

設計の目的は「要件を実装可能な構造に落とすこと」です。要件そのものは変更しないでください。

# 入力

* 要件定義書: $ARGUMENTS

  * 空の場合は `docs/requirements/requirements.md` を使用する
* 既存コード・既存設計（存在する場合）

  * リポジトリ内の既存コード
  * `docs/design/` 配下の既存設計書

既存コード・既存設計が存在する場合は、必ず確認し、整合性を考慮してください。

## 情報源の優先順位

情報源の間で食い違いがある場合は、以下の順で優先する。

1. 要件定義書
2. 既存設計書
3. 既存コード

食い違いを見つけた場合は、上位の情報源に従って設計し、差分を `01_architecture.md` の「未解決事項」に記載する。

既存コードが要件と異なる場合でも、既存コードに合わせて要件を変更してはいけない。

# 基本方針

* 作成するのは設計書のみ。実装コードは書かない
* 要件定義書にない機能を追加しない
* 要件定義書にない設計上の判断が必要な場合は、最小限の仮定を置いて進め、その内容を `01_architecture.md` の「仮定一覧」に記載する
* 要件そのものを変更・簡略化してはいけない
* 要件同士の矛盾を設計側で勝手に解消してはいけない
* 作業を停止して質問するのは、以下の場合のみとする

  * 要件に重大な矛盾がある
  * 設計を確定できないほど情報が不足している
  * OS / フレームワークの制約により、要件どおりに設計できない
* 上記に該当する問題は、どのStepで判明した場合でも、その時点で作業を停止して報告する。仮定を置いて押し切ってはいけない
* 軽微な曖昧さや実装上の選択については、合理的な仮定を置いて進める
* 要件にない改善案は「提案」として要件と明確に区別し、「提案」セクションにのみ記載する
* 提案によって要件を変更してはいけない
* 擬似コードの大量記述は行わない
* Mermaidを必要に応じて使用する
* 同じ概念・型・責務を複数の設計書で扱う場合は、定義元を明示し、矛盾する記述を作らない

# 要件IDの扱い

要件IDは、要件定義書に記載されているものをそのまま使用する。

例:

* `FR-1.3`
* `FR-2.10`
* `FR-3.8.1`
* `NFR-6.1`
* `TR-5`

以下を厳守する。

* 要件IDを独自の形式（`REQ-001` など）へ変換してはいけない
* 階層を持つIDは、末端のIDまで個別にカバーを判定する
* 親ID（例: `FR-3.8`）をカバーしただけでは、子ID（例: `FR-3.8.1`）をカバーしたことにはならない
* すべての設計項目に、対応する要件IDを明記する
* 特定の要件に紐づかない横断的な項目（ディレクトリ構成、共通基盤など）には、関連するNFR/TRを記載する
* 該当する要件IDが存在しない場合は「横断」と記載する
* 要件IDを無理にこじつけない

## 要件カバー判定

要件カバー率の母集団は、要件定義書から抽出した「末端要件ID」とする。

母集団は、`01_architecture.md` の「要件→設計対応表」の行として全件記載する。以降、この表の行数を母集団として扱う。

各要件IDは、以下の3条件をすべて満たした場合のみ「カバー済み」と判定する。

1. 対応する設計項目が存在する
2. その設計項目に当該要件IDが明記されている
3. 画面、データ、状態遷移、責務、インターフェース、エラー処理、テスト等の具体的な設計に落とし込まれている

以下は「カバー済み」として数えない。

* 仮定一覧にのみ存在する
* 未解決事項にのみ存在する
* 提案にのみ存在する
* 要件IDを記載しただけで、具体的な設計が存在しない

# 出力ファイル

以下の6ファイルのみを作成すること。

| ファイル                               | 内容                                                                                |
| ---------------------------------- | --------------------------------------------------------------------------------- |
| `docs/design/01_architecture.md`   | 全体構成、採用アーキテクチャ、レイヤー責務、依存方向、ディレクトリ構成、ターゲット構成、主要技術、状態管理方針、プラットフォーム設定、要件→設計対応表、仮定一覧、未解決事項、提案 |
| `docs/design/02_screens.md`        | 画面一覧、画面遷移、各画面の状態、表示要素、ユーザー操作、画面単位の状態遷移                                            |
| `docs/design/03_data_model.md`     | エンティティ、属性、型、リレーション、永続化方式、データ整合性、Migration方針                                       |
| `docs/design/04_modules.md`        | 主要な型・Protocol・ViewModel・Repository・Service・Engine等の責務とインターフェース、ドメインロジックの状態遷移      |
| `docs/design/05_error_handling.md` | エラー分類、発生条件、ユーザーへの表示、復旧方法、リトライ方針                                                   |
| `docs/design/06_task_breakdown.md` | テスト方針、実装タスクの分解、依存関係、完了条件、テスト観点                                                    |

以下を厳守する。

* 上記以外のファイルは作成しない
* 「要件→設計対応表」「仮定一覧」「未解決事項」「提案」は、すべて `01_architecture.md` の末尾にまとめる
* 上記4項目を、他の設計書に独立セクションとして作成しない
* 他の設計書からこれらを参照する必要がある場合は、`01_architecture.md` を参照する

# 設計書共通ルール

各設計項目には、以下を必ず記載する。

* 対応する要件ID
* 設計内容
* この設計を選んだ理由（1〜3行）
* 代替案を検討した場合は、その代替案と却下した理由

また、以下を必ず満たすこと。

1. 要件定義書に存在するすべての末端要件IDが、少なくとも1つの設計項目でカバーされている
2. 各設計項目に、対応する要件IDが記載されている
3. 設計書間で、同じ概念・型・責務の定義が矛盾していない
4. 設計上の仮定と要件そのものが明確に区別されている
5. 要件にない機能が設計に混入していない

# 特に重視する設計

## 1. 状態遷移

このアプリでは状態遷移が重要であるため、以下はMermaidで明示的に状態遷移を設計する。

| 対象               | 記載先             |
| ---------------- | --------------- |
| 新規習慣登録ウィザード      | `02_screens.md` |
| 習慣編集フロー          | `02_screens.md` |
| オンボーディング         | `02_screens.md` |
| 2分タイマー           | `04_modules.md` |
| アプリ起動時の実行セッション復元 | `04_modules.md` |
| 通知予約状態           | `04_modules.md` |
| 習慣の通常 / アーカイブ状態  | `04_modules.md` |

新規登録フローと編集フローは、別の状態遷移として扱う。

状態遷移では、最低限以下を明示する。

* State
* Event
* Guard / 条件
* Transition
* 副作用
* 遷移不能なケース
* キャンセル / 復帰 / 再試行の扱い

## 2. データ設計

要件定義書で指定されたデータモデル・永続化方針を基準とする。

特に以下を明確にする。

* Entity
* Property
* 型
* Optional / Non-optional
* Relationship
* Delete Rule
* 一意性制約
* 日付の扱い
* 派生値の計算方法
* Migration方針
* データのライフサイクル
* アーカイブ / 削除時の扱い
* アプリ本体とExtension間でデータを共有する場合の共有方式

統計値など、保存せずにSession等から算出すべき値については、その理由も記載する。

## 3. アーキテクチャ

Viewから永続化層へ直接アクセスする設計にしない。

責務を明確に分離し、少なくとも以下を整理する。

* View
* ViewModel
* Repository
* Service
* TimerEngine等のドメインロジック

各コンポーネントについて、以下を明確にする。

* Responsibility
* 所有するState
* 入力
* 出力
* 依存先
* 依存元
* テスト方法

Protocolを導入する場合は、導入理由とテスト上のメリットを記載する。

過剰な抽象化は避け、テスト容易性・責務分離・変更容易性に必要なものだけをProtocol化する。

## 4. プラットフォーム・プロジェクト設定

Appleプラットフォーム固有の設定も設計対象とする。

ただし、設計するのは要件に関係する項目のみとする。以下のリストは確認用であり、要件に関係しない項目は「対象外」と記載するだけにとどめる。このリストを理由に、要件にない機能を追加してはいけない。

要件に関係する項目については、必要性・設定内容・目的・依存関係を設計する。

* Deployment Target
* Swift / Xcodeの前提
* Framework / Package依存
* ターゲット構成（アプリ本体、Widget Extension等）
* Xcode Capability
* Entitlements
* App Groups（アプリ本体とExtension間のデータ共有）
* Info.plist
* ActivityKit
* WidgetKit
* Live Activity
* Dynamic Island
* 通知権限
* Background関連設定
* App Store提出に必要な設定

Extensionターゲットを使用する場合は、`01_architecture.md` のディレクトリ構成とターゲット構成にも反映する。

実装コードを書く必要はない。

ただし、設定項目そのものは曖昧にせず、「何を設定するのか」「なぜ必要なのか」まで明記する。

## 5. テスト設計

テスト方針は `06_task_breakdown.md` の冒頭に記載する。

特に以下の観点を考慮する。

* 正常系
* 境界値
* 時刻・日付境界
* 強制終了 / 復帰
* バックグラウンド
* 通知許可状態
* 空データ
* 最大件数
* 日本語 / 英語
* Dynamic Type
* VoiceOver
* Reduce Motion
* ダークモード
* エラー時の復旧

`TimerEngine` 等の時間に依存するロジックは、テスト可能な構造を優先する。

例えば、現在時刻を直接参照するのではなく、テスト時に現在時刻を差し替えられる構造などを検討する。

# タスク分解（06_task_breakdown.md）

後続の開発では、このファイルをチケット起票の元資料として使用する。

## 粒度

* 各タスクは半日〜1日程度で完了できる粒度に分解する
* 1タスクに複数の独立した機能をまとめすぎない
* 実装と、それに対応する単体テストを同一タスクに含める
* テストだけを後回しにした独立タスクは作らない

## 各タスクに含める項目

* タイトル
* 概要
* 対応要件ID
* 参照する設計書
* 完了条件
* テスト観点
* 依存タスク

完了条件には、原則として以下を含める。

> 実装が完了し、対象の単体テストが通ること

## タスク順序

タスクは依存関係順に並べ、以下のフェーズで整理する。

1. 基盤
2. データ
3. ドメインロジック
4. UI
5. OS / システム連携
6. 統合
7. 結合テスト・手動確認
8. リリース対応

単純なファイル作成順ではなく、実際の依存関係を優先する。

# 進め方

## Step 1: 要件分析

要件定義書と、既存コード・既存設計を確認し、以下を整理する。

* 末端要件ID一覧
* 明確な要件
* 設計に委ねられている事項
* 軽微な曖昧点
* 重大な矛盾
* 設計不能な不足情報
* 画面一覧
* ドメイン概念一覧
* OS / 外部システムとの連携一覧
* 状態遷移対象一覧
* 主要な非機能要件

この分析結果は、別ファイルとして保存しない。

ただし「末端要件ID一覧」は、Step 2で作成する `01_architecture.md` の「要件→設計対応表」に全件転記する。

重大な矛盾や、設計を確定できないほどの不足情報がある場合は、ここで作業を停止して質問する。

それ以外は合理的な仮定を置いて進め、仮定を `01_architecture.md` の「仮定一覧」に記載する。

## Step 2: 全体アーキテクチャ

`01_architecture.md` を作成し、以下を確定する。

* アーキテクチャ
* レイヤー責務
* 依存方向
* ディレクトリ構成
* ターゲット構成
* 主要コンポーネント
* 状態管理方針
* プラットフォーム / Xcode設定
* 外部依存

`01_architecture.md` の末尾には、以下の順で記載する。

1. 要件→設計対応表
2. 仮定一覧
3. 未解決事項
4. 提案

要件→設計対応表については、以下を守る。

* Step 1で抽出した末端要件IDを全件記載する
* Step 2の時点では、`01_architecture.md` で設計した項目のみ対応先を記入する
* それ以外の行は「未設計」とする
* 未作成の設計書を対応先として先に書いてはいけない

### Step 2完了後

以下を簡潔に報告して、承認を待つこと。

* 採用アーキテクチャと理由
* レイヤー構成
* 主要コンポーネント
* 主要な依存関係
* ターゲット構成
* プラットフォーム関連の重要設定
* 重要な仮定
* 重大ではないが確認したい点
* 設計上の未解決事項

**承認されるまでStep 3以降には進まない。**

## Step 3: 画面・データ・モジュール

承認後、以下の順で作成する。

1. `02_screens.md`
2. `03_data_model.md`
3. `04_modules.md`
4. `05_error_handling.md`

各設計書の作成後に、以下を確認する。

* 要件IDとの対応
* 状態遷移の整合性
* データモデルとの整合性
* モジュール責務との整合性
* それ以前に作成した設計書との矛盾

確認後、`01_architecture.md` の以下を更新する。

* 要件→設計対応表（「未設計」の行を、作成した設計書の対応先に置き換える）
* 仮定一覧
* 未解決事項
* 提案

## Step 4: タスク分解

`06_task_breakdown.md` を作成する。

設計書から実装タスクへ、可能な限り機械的に落とし込めるようにする。

各タスクには、対応要件IDと参照設計書を明記する。

## Step 5: セルフレビュー

以下を確認する。

### 要件

* 要件→設計対応表から算出したカバー率が100%か

  * 100%未達の場合は、未カバーのIDとその理由をすべて列挙する
* 要件→設計対応表に「未設計」の行が残っていないか
* 各設計項目に要件IDが記載されているか
* 要件にない機能を追加していないか

### 設計

* 設計書間で矛盾していないか
* 指定したすべての状態遷移が、指定した記載先で定義されているか
* データモデルとRepositoryの責務が一致しているか
* View / ViewModel / Repository / Service / Engineの責務が重複していないか
* 依存方向が逆転していないか

### プラットフォーム

* Framework / Capability / Entitlement / App Groups / Info.plist等に漏れがないか
* ターゲット構成とディレクトリ構成が一致しているか
* 要件に関係しない項目が「対象外」になっており、設計に混入していないか
* Live Activity / 通知 / バックグラウンド等のOS制約と設計が矛盾していないか

### テスト

* 主要な正常系がカバーされているか
* 境界値がカバーされているか
* 時刻・日付関連の境界がカバーされているか
* 強制終了 / 復帰がカバーされているか
* 通知状態がカバーされているか
* UI / アクセシビリティ要件がカバーされているか

### タスク

* タスク粒度が半日〜1日程度か
* 各タスクに完了条件があるか
* 単体テストが実装タスクに含まれているか
* 依存関係に漏れがないか
* 実装順が依存関係と整合しているか

# 最終報告

最終報告は簡潔にまとめ、以下を出力する。

* 作成したファイル一覧
* 要件カバー率（カバー済み末端ID数 / 全末端ID数）
* 未カバーの要件IDと理由（ある場合）
* 未解決事項
* 仮定した事項
* 設計上の重要な判断
* 提案事項
