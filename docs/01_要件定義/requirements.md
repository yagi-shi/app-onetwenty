## 1. コンセプト

**記録するアプリではなく、実行するアプリ。**

習慣化アプリの大半は「やったかどうかをユーザーが自己申告する」記録ツールである。本アプリは自己申告によるチェックインを提供せず、**タイマーを起動し、120秒を経過させたことだけを完了と定義する**。

> **完了判定の線引きについて（既知の抜け穴）**
> FR-2.10 でバックグラウンド継続を認め、FR-2.11 で Live Activity を提供する以上、「タイマーを起動して放置する」「起動直後にアプリを終了し2分後に開き直す」といった経路でも完了として記録される。この抜け穴は認識したうえで受け入れる。
> 理由は2つある。第一に、フォアグラウンド滞在を条件にすると Live Activity の存在意義が消え、TR-1（経過時間は `startedAt` との差分で算出）とも衝突する。第二に、本アプリの差別化はワンタップの自己申告を排すること自体にあり、**2分待たなければ記録されない**という事実は上記の経路でも維持される。
> したがって完了の定義は「アプリ内で2分間を過ごしたこと」ではなく「タイマーを起動し、120秒を経過させたこと」である。

理論的な下敷きは『Atomic Habits』（James Clear）の2分ルール（新しい習慣は2分以内で終わるレベルまで分解すべき）だが、本アプリが実装するのはその後半部分——「2分で止めろ」——である。

### プロダクト原則

| #   | 原則                           | 実装                                           |
| --- | ------------------------------ | ---------------------------------------------- |
| 1   | 実行したことだけを記録する     | 手動チェックインを提供しない（FR-3.2）         |
| 2   | 2分を超えさせない              | 延長・一時停止・スキップを実装しない（FR-2.3） |
| 3   | 分解を通過しないと登録できない | ウィザードを必ず経由させる（FR-1）             |
| 4   | 記録できる実行時間に上限を設ける | 1日に記録できるのは合計6分まで（FR-4）       |

### ストア表記

```
ja  名前        : OneTwenty: 2分ルールの習慣化タイマー
    サブタイトル : チェックインなし。2分やった人だけ記録される

en  名前        : OneTwenty: 2-Minute Habits
    サブタイトル : Not a tracker. A two-minute timer.
```

- 日本語のキーワードフィールドはカンマ区切りとする（スペース区切りは形態素解析で意図しない分割が起きる）
- `atomic habits` 等の書籍名は商標のためキーワードに使用しない
- 説明文の冒頭で「OneTwenty＝120秒」を明示し、アイコンに `120` を含めることで読みの曖昧さを補う

- 初回起動時のオンボーディング（2画面。FR-7）

### v1.0 に含まない

| 項目                                    | 理由 / 対応時期                                                               |
| --------------------------------------- | ----------------------------------------------------------------------------- |
| ホーム画面ウィジェット                  | v1.1。役割は「今日の3件の進捗表示＋タップでタイマー即起動」に確定済み（§5.1） |

| ソーシャル機能・共有                    | 対象外                                                                        |
| Apple Watch                             | v1.2以降                                                                      |
| Android版                               | 対応しない                                                                    |

## 4. 機能要件

### FR-1: 習慣の登録（分解ウィザード）

| ID       | 要件                                                                                                                                                                                             |
| -------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| FR-1.1   | ユーザーは「やりたいこと」を自由入力できる                                                                                                                                                       |
| FR-1.2   | 入力値をそのまま習慣として登録することはできない。必ず分解ウィザードを経由する                                                                                                                   |
| FR-1.3   | ウィザードは**1問1画面**で進行する。「それは今から2分で終わりますか？」を起点に、Noの場合「その最初の1アクションは何ですか？」を繰り返す                                                         |
| FR-1.3.1 | 再分解のループは**3回目のNoで打ち切り**、FR-1.7 の汎用パターン3種の選択に強制的に誘導する                                                                                                        |
| FR-1.4   | 最終的な習慣名は1文に制限する。**品詞による判定は行わない**（日本語は動詞が文末に来るため「動詞で始まる」という規則は成立しない）。行動として妥当かの判断は FR-1.5.2 のY/N確認に委ねる |
| FR-1.4.1 | 文字数の上限は**言語別**とする。**日本語30文字 / 英語60文字**とし（TODO 2 の実測で確定）、**表示言語が日本語なら30、それ以外はすべて60**を適用する（NFR-6.1）。英語は同じ内容を表すのに日本語の約2倍の文字数を要するため、一律にすると英語ユーザーだけが正当な入力を拒否される |
| FR-1.4.2 | 文字数は **`String.count`（グラフェムクラスタ数）**で数える。絵文字や結合文字は1文字として扱う |
| FR-1.4.3 | 文字数の上限は**新規入力の検証にのみ適用する**。すでに保存済みの `title` を遡って無効にしない。端末の表示言語を変更した結果、既存の `title` が現在の上限を超える状態は正常として扱い、ホーム画面・統計画面・通知のいずれにも影響を与えない |
| FR-1.5   | 目標表現の検出は二段構えとする（下記 FR-1.5.1 / FR-1.5.2）                                                                                                                                       |
| FR-1.5.1 | **ハードルールによる拒否は文字数超過（FR-1.4.1）のみ**とする。頻度副詞・目標表現の語尾を検出した場合の挙動は、下記の**2分岐**とする（FR-1.5.1.2 / FR-1.5.1.3） |
| FR-1.5.1.1 | 検出対象の語は **[detection-terms.md](./detection-terms.md) に定義した閉じたリスト**とする。要件定義書本文には例示を置かない。リストにない語は検出しない（誤検出より検出漏れを許容する）。**表示言語が日本語なら日本語リスト、それ以外は英語リストを適用する**（NFR-6.1） |
| FR-1.5.1.4 | 英語の活用形（keep / keeps / keeping / kept 等）は**リストに全形を列挙して吸収する**。形態素解析やステミングは行わない。検出ロジックは日英共通とし、言語差はデータ側に閉じ込める。照合は部分一致を基本とし、**英数字で始まる（終わる）語だけは、その側が単語の区切りである場合に限って一致とみなす**（"entry to" の中の "try to" や "housekeeping" の中の "keep" を検出しない。日本語の語は端が英数字ではないため、従来どおり文中のどこでも一致する） |
| FR-1.5.1.2 | **頻度副詞を検出した場合**：当該語を機械的に除去した文を代替案として提示し、ユーザーが採否を選ぶ。採用すれば除去後の文で次に進み、不採用なら入力をそのまま次に進める。再分解には戻さない |
| FR-1.5.1.3 | **目標表現の語尾を検出した場合**：代替案は提示せず、**FR-1.3 の再分解に戻す**（「それは目標です。最初の1アクションは何ですか？」）。再分解の回数は FR-1.3.1 の上限に算入する |
| FR-1.5.2 | **ソフト確認（委譲）**: ハードルールを通過した入力についても、登録前に「これは2分で終わりますか？」のY/N確認を必ず1回挟む。Noの場合は再分解に戻る                                                |
| FR-1.6   | 頻出カテゴリ（運動・読書・掃除・語学・瞑想など）については分解済みテンプレートを提示する。**リリース可否の下限は日英各20パターン**とし、50パターンを目標値とする                                  |
| FR-1.7   | テンプレートに該当しない入力に対しては、**汎用の分解パターン3種**を選択肢として提示する（下記 FR-1.7.1）                                                                                         |
| FR-1.7.1 | ① 道具を用意する／② その場所に行く／③ 最小単位を1つやる。ユーザーは型を選んでから具体を記述する                                                                                                  |
| FR-1.8   | 分解前の入力（originalIntent）も保持する。テンプレートから直接選んだ場合は**ユーザーの最初の自由入力**を、FR-6.4 で習慣名を編集した場合は**既存の値を書き換えず維持する**                        |
| FR-1.9   | 登録可能な習慣は**最大3件**。4件目の登録は不可。アーカイブ済み（`archivedAt != nil`）の習慣は件数に含めない                                                                                      |
| FR-1.10  | ウィザードは**いつでもキャンセルできる**。キャンセル導線は全画面の同じ位置に常時表示する。確認ダイアログは挟まない                                                                               |
| FR-1.10.1 | キャンセル時、**途中の入力と分解状態はすべて破棄する**。未完成の分解状態を永続化しない。次回ウィザードを開いたときは最初の自由入力から始める                                                    |
| FR-1.10.2 | キャンセル後の遷移先は**起動元の画面**とする。新規登録（ホームまたは FR-7.6 のオンボーディング直後）からの起動ならホーム画面、編集（FR-6.4）からの起動なら**設定画面の習慣管理セクション**に戻る。オンボーディング直後にキャンセルした場合は**習慣0件のホーム画面**（「＋」のプレースホルダと「習慣を追加」）を表示し、オンボーディングには戻さない |
| FR-1.10.3 | ウィザードの各画面で**1問前に戻る操作を提供する**。戻った場合、その問より後の入力は破棄する。**最初の問より前には戻れない**（やめる場合は FR-1.10 のキャンセルを使う） |
| FR-1.10.4 | 戻る操作を行っても、**FR-1.3.1 の再分解カウンタは減らさない**（累積値として扱う）。上限（3回目のNo）に到達した後に戻った場合、再び先へ進むと FR-1.7 の汎用パターン画面に入る |
| FR-1.10.5 | **編集フロー（FR-6.4）の場合**、キャンセルしても既存の `title` と `originalIntent` を変更しない。編集が確定するのは FR-1.5.2 のソフト確認を通過して登録した時点のみ |

> 分解する主体はユーザーであり、アプリは質問と検証のみを担う。分解案の生成は行わないため、v1.0でLLMは不要。FR-1.5.1 と FR-1.7 は決定的なロジックであり、Swift Testing の主要な検証対象とする。
> FR-1.4 から品詞判定を外したのは実装可能性の判断による。日本語の短い断片に対する形態素解析は誤判定が起きやすく、正しい入力を拒否する事故はこのアプリで最も避けたい失敗である。
> FR-1.5.1 から禁止語によるハード拒否を外したのも同じ理由である。日本語には語境がないため部分一致でしか検出できず、「毎日新聞を1ページ読む」「必ず持ち歩く水筒を洗う」のような正当な入力が弾かれる。検出は維持しつつ、拒否ではなく代替案の提示に変えることで、原則3の意図（目標ではなく行動を登録させる）を保ったまま誤拒否をなくす。
> 結果としてハード拒否は文字数制限のみとなり、行動として妥当かの判断は FR-1.5.2 のソフト確認が担う。
> FR-1.4.3 で保存済みの `title` に上限を遡及適用しないのは、端末の表示言語を変更したユーザーが自分の習慣名を編集できなくなるためである。英語環境で45文字の習慣名を登録した後に端末を日本語へ切り替えると、上限は30に変わる。遡及適用すると、編集画面を開いた瞬間に45文字が上限違反として拒否され、直す手段がないまま行き詰まる。上限は新規入力の検証にのみ使い、既存の値は FR-6.4.2.1 のとおり文字数を見せながら編集させる。
> FR-1.4.1 で上限を言語別にしたのは、文字数が言語によって情報密度を大きく変えるためである。「単語アプリを開いて1枚やる」は13文字だが、同じ内容の "Open the vocabulary app and do one card" は39文字あり、一律30文字では英語ユーザーだけが正当な入力を拒否される。これは FR-1.4 の注記が最も避けたいとした事故そのものである。暫定値としていた 30 / 60 は、TODO 2 のテンプレート作成時の実測（日英各41件。最長は日本語14文字・英語35文字）で十分な余裕があることを確認し、そのまま確定した。
> FR-1.5.1 を2分岐にしたのは、**機械的に代替案を生成できるかどうか**で扱いが変わるためである。頻度副詞は「毎日新聞を1ページ読む」から「毎日」を除去すれば妥当な文が残るため、決定的なロジックで代替案を出せる。一方「読書を続ける」を「本を1ページ開く」に言い換えるには意味の理解が必要で、v1.0でLLMを使わない方針では生成できない。したがって目標表現は代替案を出さず、ユーザー自身に再分解させる（原則3と一致する）。
> FR-1.5.1.4 で英語の語だけ単語の区切りを見るのは、英語では部分一致が正当な入力を止めてしまうためである。"Add an entry to my journal" は "en**try to**" が "try to" に一致して目標表現とみなされ、FR-1.5.1.3 により再分解へ戻される。同じ文を入れ直しても通らないため、頻度副詞（不採用を選べる）と違って実質的な拒否になる。日本語の検出語は語尾が長く具体的で同じ問題が起きにくいので、部分一致のままとする。判定は語の端の文字で決まり、表示言語による分岐は持たない。
> ウィザードの状態遷移は**設計書で状態遷移図として定義する**。本書では個々の規則のみを規定する。対象は次のとおり。
> - **新規登録フロー**：FR-1.3 のループ、FR-1.6 のテンプレート提示、FR-1.7 の汎用パターン、FR-1.5.1.2 / FR-1.5.1.3 の2分岐、FR-1.5.2 の最終確認
> - **編集フロー**（FR-6.4.2 〜 FR-6.4.5）：新規登録とは通る段階が異なるため、**別の遷移として描く**。目標表現の検出で再分解へ入る分岐（FR-6.4.4）と、上限到達で汎用パターンへ合流する分岐（FR-6.4.5）を必ず含める
> - 両フロー共通：FR-1.10 のキャンセル、FR-1.10.3 の戻る、FR-1.10.4 のカウンタの扱い
> FR-1.10 でキャンセルを提供するのは、FR-7.6 によりオンボーディング直後のユーザーが最初に到達する画面がウィザードになるためである。ここで抜けられないと、分解に詰まったユーザーがアプリごと離脱する。FR-7.2（オンボーディングはスキップ不可）と方針が異なるのは、オンボーディングが2画面を読むだけなのに対し、ウィザードはユーザー自身に分解という思考を要求するためである。
> FR-1.10.1 で入力を破棄するのは、未完成の分解状態を永続化するモデルとテストを増やさないためである。ウィザードは最短で数問なので、やり直しのコストは小さい。

### FR-2: 実行（2分タイマー）

| ID      | 要件                                                                                                                |
| ------- | ------------------------------------------------------------------------------------------------------------------- |
| FR-2.1  | ホーム画面の習慣をタップすると即座にタイマーが開始する。確認ダイアログは表示しない                                  |
| FR-2.2  | タイマーは120秒固定。時間変更は不可                                                                                 |
| FR-2.3  | 一時停止・延長・スキップの操作を提供しない                                                                          |
| FR-2.4  | 表現は**タイマーリング（円形プログレス）＋残り秒数の数字**とする。アクセント色1色で描画する                        |
| FR-2.5  | 中断は**下方向スワイプ**で行う。確認ダイアログは挟まない。中断したセッションは記録せず破棄する（FR-3.3）            |
| FR-2.5.2 | **VoiceOver が有効な場合は、iOS 標準のエスケープ操作（2本指の Z 字スクラブ）でも中断できる**。下方向スワイプは画面をなぞって読み上げる操作と両立しないため、中断の**代替入力**として認める。中断後の扱い（記録せず破棄）は FR-2.5 と同じであり、新しい機能ではない（NFR-4.2） |
| FR-2.5.1 | 誤爆を防ぐため、中断ジェスチャは次を満たす。①**120pt以上のドラッグ**で発火し、それ未満は元の位置に戻る ②ドラッグ中はタイマーリングが指に追従して不透明度を下げ、離せば中断されることを予告する ③通知センターとの干渉を避けるため、**safe area 上端から80pt以内で開始したドラッグには反応しない** |
| FR-2.6  | 中断した習慣は同日中に**何度でも再挑戦できる**。再挑戦は常に0秒から開始する                                         |
| FR-2.7  | 完了時は**サウンドとハプティクスを併用**する。アプリがフォアグラウンドにある場合に限る（フォアグラウンド外は FR-2.13） |
| FR-2.7.1 | サウンドはサイレントスイッチに従わせる。`AVAudioSession` のカテゴリは **`.ambient`** とする（`.playback` を使うとサイレント時にも鳴ってしまう） |
| FR-2.7.2 | ハプティクスはサイレントスイッチの影響を受けず、端末の「システムハプティクス」設定に従う。**サイレント時は無音＋振動のみになる**が、これを意図した挙動とする |
| FR-2.8  | 完了音は達成を祝う音ではなく、**終わりを告げる短い終止音**とする                                                    |
| FR-2.9  | 完了時の文言は**毎回変わる短い一言**とする。褒める方向ではなく、終了を告げる方向で振る                              |
| FR-2.10 | アプリがバックグラウンドに移行しても計測を継続する                                                                  |
| FR-2.11 | Live Activity に残り時間を表示する。Dynamic Island 搭載機種では Dynamic Island にも表示する                        |
| FR-2.11.0 | Dynamic Island は搭載機種が限られるため、**非搭載機種ではロック画面・バナーの Live Activity のみ**で成立する設計とする。Dynamic Island 固有の表示を前提にした導線を作らない |
| FR-2.11.1 | Live Activity は WidgetKit 基盤のため**秒単位の再描画ができない**。残り時間は `Text(timerInterval:countsDown:)` / `ProgressView(timerInterval:)` 等のシステム描画APIで表現し、**アプリ内のタイマーリング（FR-2.4）と同一の見た目は再現しない**ことを前提にデザインする |
| FR-2.11.2 | Live Activity には `staleDate`（開始から120秒後）を指定し、アプリが動いていなくても120秒経過後は**終了した見た目**（残り0:00・終了表示）に切り替わるようにする。表示の消去はアプリ自身にしかできないため、**次にアプリがアクティブになった時点で即時消去する**（`dismissalPolicy: .immediate`）。アプリを開かない場合の消去は OS の上限（最大8時間＋ロック画面で最大4時間）に委ねる |
| FR-2.12 | 実行中は下方向スワイプ以外の画面遷移を行えない。**ただし FR-2.5.2 のエスケープ操作は例外とする**（中断と同じ扱いであり、他の画面へ遷移する手段ではない）  |
| FR-2.13 | アプリがフォアグラウンドにない状態で120秒に到達した場合、**ローカル通知で2分の経過を伝える**。通知はタイマー開始時に120秒後で予約し、フォアグラウンドでの完了時および中断時にはキャンセルする。Live Activity は FR-2.11.2 のとおり終了した見た目に切り替わり、次にアプリがアクティブになった時点で消去する |
| FR-2.14 | FR-2.13 の通知文言は**習慣名・連続日数・残り件数を含まない固定文言**とし（FR-5.3 と同じ方針）、**「完了した」「記録された」と断定しない**。経過の事実のみを伝える（例：「2分経ちました」）。記録の確定は次回アプリ起動時に行われるため（FR-2.15 / FR-2.15.1） |
| FR-2.14.1 | FR-2.13 の完了通知は**設定の「通知のオン/オフ」（FR-5.5）に依存しない**。ユーザー自身が2分前に開始したタイマーの結果を伝えるものであり、タイマー機能の一部として扱う。OSの通知許可が拒否されている場合のみ送られず、その場合は Live Activity が伝達を担う |
| FR-2.15 | タイマー実行中にアプリが強制終了された場合、次回起動時に `startedAt` からの経過時間で判定する。120秒以上経過していれば完了として記録し、未満であれば未完了として破棄する |
| FR-2.15.1 | ただし `startedAt` から**24時間以上**経過している場合は、経過時間によらず破棄する。数日後に起動したセッションが FR-3.10 の日付帰属によって過去の日に完了として書き込まれ、ヒートマップと連続日数を遡って書き換えることを防ぐ |

> FR-2.11.2 で「自動消去」を求めないのは OS の制約による。Live Activity の終了（`end()`）はアプリ自身が呼ぶ必要があるが、バックグラウンドのアプリは停止しており120秒の時点でコードを動かせない。外部から終了させるには ActivityKit のプッシュ更新が必要で、サーバーを要するため TR-4 に反する。AlarmKit（iOS 26）のシステム管理カウントダウンはサイレントモードを突破して鳴るため FR-2.7.1 と両立しない。したがって「終わった見た目への切り替え」までを自動とし、消去は次回アクティブ化時とする。
> FR-2.9 の文言バリエーションは報酬設計になりうる。「よくやった」系の賞賛は原則2（継続を促さない）と衝突するため採用しない。日英それぞれ20〜30本を用意する。
> FR-2.15 を「一律中断」としないのは、TR-1（経過時間は常に `startedAt` との差分で算出）と整合させるためである。中断扱いにすると、予約済み通知が完了を告げた直後にアプリ内で未完了と表示される矛盾が生じる。iOS にはアプリの強制終了を検知して予約済み通知を取り消す信頼できる手段がないため、この矛盾は解消できない。また強制終了は誤操作や端末のメモリ解放でも起こり、ユーザーの意図と一致しない。これが生む抜け穴は §1 の注記で明示的に受け入れている。
> FR-2.9（毎回変わる）と FR-2.14（固定文言）で方針が異なるのは、通知が**履歴として端末に残る**ためである。同じ文言が並ぶ方が通知センターでは自然であり、毎回変わる一言は画面上で一度だけ見せる演出として機能する。
> FR-2.14 で通知に「完了」と書かないのは、通知が発火した時点では記録がまだ確定していないためである。ローカル通知は予約時刻に必ず発火するが、Session の記録は次回アプリ起動時に FR-2.15 / FR-2.15.1 の判定を経て確定する。24時間以上開かなかった場合は破棄されるため、通知で完了を断定すると実際の記録と食い違う。経過の事実のみを伝えれば、どちらの経路でも嘘にならない。

### FR-3: 記録

| ID       | 要件                                                                                                                   |
| -------- | ---------------------------------------------------------------------------------------------------------------------- |
| FR-3.1   | 完了の定義は「**タイマーを起動し、120秒を経過させたこと**」のみとする（§1の定義と同一）                                |
| FR-3.2   | **手動チェックイン（タイマーを使わない完了記録）を提供しない。これが本アプリの中核的な差別化要因である**               |
| FR-3.3   | **中断されたセッションは永続化しない。** 完了した Session のみを保存する                                               |
| FR-3.4   | 完了時のメモ・感想・言い訳の入力欄を提供しない                                                                         |
| FR-3.5   | **習慣ごとの**現在の連続日数は**ホーム画面の習慣リング脇**に表示する。統計画面には置かない                             |
| FR-3.5.1 | 習慣ごとの連続日数の定義は「**その習慣の Session が存在する日（FR-3.10 の日付帰属による）が連続している日数**」とする。統計画面の全体値（FR-3.9、単位は「1件以上完了した日」）とは集計単位が異なる |
| FR-3.5.2 | **当日がまだ未完了の場合は、前日までの連続日数をそのまま表示する**（0にリセットしない）。連続が途切れたと判定するのは、前日が未完了だった場合のみ。毎朝0が並ぶ表示は FR-3.6（煽らない）の意図に反する |
| FR-3.5.3 | 習慣の `createdAt` より前の日は連続の判定対象に含めない。アーカイブ済み習慣はホーム画面に表示されないため、連続日数も表示しない |
| FR-3.5.4 | **連続日数が0の場合は、連続日数そのものを表示しない**（「0日」とは出さない）。登録当日でまだ完了していない場合と、連続が途切れた後の両方に同じ規則を適用する。FR-3.6（途切れても煽らない）と整合させるため |
| FR-3.6   | 連続記録が途切れた場合も、警告色や煽り文言を表示しない                                                                 |
| FR-3.7   | 統計画面は**標準文字サイズで1画面に収め**、スクロールを発生させない。Dynamic Type の拡大時のみ縦スクロールを許容する    |
| FR-3.8   | 履歴表示は**ヒートマップ1枚**とする。**月送り・年送りのUIは提供しない**。表示範囲は**直近12週間（84日）固定**とする     |
| FR-3.8.1 | ヒートマップは習慣ごとに分けず1枚に統合し、**濃淡でその日の達成率を表す**。分子はその日の完了件数、分母は**その日に有効だった習慣数**（アーカイブ済みの習慣も `archivedAt` 以前の日については分母に含める）。登録0件の日は空欄とする。色はアクセント1色の濃度で表現する |
| FR-3.9   | 統計画面に置く数値は**現在の連続日数・最長連続日数・通算完了回数の3つのみ**とする。いずれも**アプリ全体で1つの数値**とし、連続の単位は「1件以上完了した日」に統一する |
| FR-3.9.1 | 統計画面では、**値が0の場合も「0」を表示する**（ホーム画面の FR-3.5.4 とは扱いが異なる）。3つの数値が常に揃った状態を保ち、FR-3.7（1画面に収める）のレイアウトを安定させる |
| FR-3.9.2 | ヒートマップは非インタラクティブとする。セルのタップ・ロングプレス・ツールチップを提供しない                           |
| FR-3.10  | セッションの日付帰属は `startedAt` のローカル日付とする。23:59に開始し0:01に完了したセッションは**開始日**の完了として集計する |
| FR-3.11  | 統計画面への導線は**ホーム画面右上の小さなアイコン1つ**とする。完了時・通知・オンボーディングから統計へ誘導しない（FR-4.3） |
| FR-3.12  | アーカイブは一方通行のため（FR-6.3）、`archivedAt` が事後的に変わることはない。**アーカイブに由来して**ヒートマップの分母と連続日数が過去に遡って変化する経路は存在しない。ただし端末のタイムゾーン変更は例外とする（日付は保存せず、その時点のタイムゾーンで算出するため。FR-3.10） |

> FR-3.8 の意図は「アプリに長く滞在させない」ことであり、禁じる対象は過去を遡らせる月送りUIである。ヒートマップは1画面に収まり一望できるため、滞在時間を伸ばさず FR-3.7 とも整合する。
> FR-3.8.1 を絶対件数ではなく達成率としたのは、登録1件のユーザーが最濃に到達できず、ヒートマップが機能しなくなるためである。達成率であれば登録件数によらず「その日やり切ったか」が一目で分かる。
> FR-3.3 を「保存しない」に変更したのは、中断セッションを表示する画面が要件上どこにも存在しないためである。原則1（実行したことだけを記録する）および FR-3.4（言い訳を入力させない）とも整合する。
> **FR-3.9.1（統計は0を出す）と FR-3.5.4（ホームは0を隠す）の非対称は意図的である。** ホームは毎日必ず目に入る画面で、そこに0が並ぶと FR-3.6 が禁じた煽りに近づく。一方、統計画面はユーザーが自ら開きに行く画面であり、積み上げを確認する目的で訪れるため、0を事実として示しても圧にはならない。加えて FR-3.7（標準文字サイズで1画面に収める）を満たすうえで、数値の有無で枠が伸縮しない方がレイアウトが安定する。
> FR-3.9 をアプリ全体の単一値に統一したのは、定義の異なる数値を並べないためである。「筋トレ: 3日 / 読書: 7日」（習慣単位）と「最長連続: 20日」（1件以上完了した日）が同じ画面にあると、比較できない数値の比較を誘発する。習慣ごとの連続日数はホーム画面の習慣リング脇に移し、統計画面の数値は3つに絞る。
> FR-3.8 を年間から12週間に縮めたのは2つの理由による。第一に、Dynamic Type の最大サイズで年間ヒートマップと数値群を1画面に収めることは物理的に不可能で、FR-3.7 と NFR-4 が両立しない。第二に、年間表示は新規ユーザーに「371マス中1マスだけが色付きの画面」を見せることになり、積み上げを示すはずの画面が未達成期間を最も強く可視化してしまう（FR-3.6 の思想と逆行する）。12週なら84セルで1セル約20pt となり、視認性も確保できる。
> FR-3.8 の「月送りUIを禁じる」という当初の意図（過去を遡らせない）は、範囲を縮めても失われない。

### FR-4: 1日の上限

| ID     | 要件                                                                                                                                                       |
| ------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------- |
| FR-4.1 | 1日に**完了**できるのは登録済み習慣の1回ずつ、最大3回（合計6分）とする                                                                                     |
| FR-4.2 | 同一習慣を完了後に当日中に再実行する手段を提供しない。完了済みの習慣はホーム上で完了状態に固定され、タップしてもタイマーは起動しない。エラー表示は行わない。当日かどうかの判定は FR-3.10 の日付帰属に従う |
| FR-4.3 | **本日終了専用の画面は設けない。** 全習慣完了時は、ホーム画面の**登録されている全習慣リングが満ちた状態**に短い文言を1行添えることで表現する。統計への誘導や次回通知時刻の提示は行わない |
| FR-4.3.1 | ホーム画面の習慣リングは**登録件数分だけ**表示する。未使用の枠は空の習慣リングではなく「＋」のプレースホルダとして視覚的に区別する。習慣1件のユーザーに空の習慣リング2つを常時見せない |
| FR-4.3.2 | 完了済みの習慣リングは**ボタンとして扱わない**。VoiceOver でボタンと読み上げられないようにし（`.isButton` トレイトを外す）、視覚的にも不活性であることを表現する。タップに無反応な点は維持するが、押せそうに見せない |
| FR-4.4 | 日付の切り替わりはユーザーのローカルタイムゾーンの0時とする。日跨ぎセッションの帰属は FR-3.10 に従う。**FR-4.5 の切り替え契機を経た後は**、翌日分として同じ習慣を再度実行できる |
| FR-4.5 | ホーム画面の表示日を切り替える契機は次の2つに**一本化**する。①シーンがアクティブになった時点（起動・フォアグラウンド復帰）②フォアグラウンド滞在中に日付変更通知（`.NSCalendarDayChanged`）を受信した時点。いずれの契機でも、その時点の当日分の完了状態へ更新する |
| FR-4.5.1 | 完了フィードバック（FR-2.7 のサウンド・ハプティクスと FR-2.9 の文言）の表示中は、**ホーム画面の習慣リングが見えない状態にする**。完了した瞬間にリングが満ちて即座に未完了へ戻る表示を避けるためであり、帰属日を保持する仕組みは設けない。フィードバック終了後は FR-4.5 の規則に従い、日跨ぎ完了の場合その習慣は当日未完了として表示される |

> **FR-4.1 の「最大3回」は既知の抜け穴を持つ。** 上限は、同時に登録できる習慣が3件（FR-1.9）で各習慣が1日1回（FR-4.2）という構造から生じるものであり、習慣を問わない1日の回数上限としては強制しない。「当日3件完了 → 1件アーカイブ → 新規登録 → 完了」の経路で4回目以降を記録できるが、取り消せないアーカイブ（FR-6.3.1）とウィザードの再通過を要するため、認識したうえで受け入れる。
> FR-4.2 はユーザーの行動を制限するものではない。2分を超えて続けたいユーザーはアプリ外で継続できる。アプリが記録しないだけであり、実世界の行動には介入しない。
> FR-4.3 は原則4に基づく。統計への誘導や次回通知時刻の提示は滞在時間を伸ばすか「また来い」という圧を生むため行わない。
> FR-4.5.1 を改訂したのは、設計で「完了文言をタイマー画面に2.5秒表示してからホームへ戻す」と決めたためである。この構成ではフィードバック中ホーム画面はタイマー画面に覆われており、避けたかった「満ちて即座に戻る」表示は起こりえない。一方で帰属日を保持する仕組みを入れると、前日に完了していた別の習慣が当日も完了済みと判定され、FR-4.4 が認める再実行ができなくなる。したがって仕組みは設けず、覆われていること自体を要件とする。
> FR-3.12 に例外を加えたのは、日付を保存せずその時点のタイムゾーンで算出する方式（FR-3.10）の帰結である。タイムゾーンを変更すると過去の Session の帰属日が移りうる。これを防ぐには帰属日を保存時に確定させる必要があり、タイムゾーンをまたいで移動したユーザーの表示が実態とずれる副作用が出るため、変化を受け入れる。
> FR-4.5 の契機を一本化したのは、旧版が「アプリを再起動または再度フォアグラウンド化した時点」としており、**アプリをフォアグラウンドに置いたまま0時を跨いだ場合に表示が更新されず**、FR-4.4 が認める再実行ができなくなっていたためである。日付変更通知を契機に加えることで、滞在したままでも切り替わる。

| FR-5.4.1 | 習慣0件は到達可能な状態である。①FR-1.10.2 でウィザードをキャンセルした直後 ②FR-6.3 で登録済み習慣をすべてアーカイブした場合。②では通知許可を取得済みで予約も残っているため、0件になった時点で**リマインダーの全予約をキャンセルする**（TR-5）。習慣が1件でも登録された時点で予約し直す |
| FR-5.5 | 通知のオフを設定から選択できる。**対象は FR-5.1 のリマインダー通知のみ**とし、FR-2.13 のバックグラウンド完了通知は設定に依存せず常に動作する |
| FR-5.6 | 通知許可は**初回のタイマー開始直前、または初回の習慣登録完了直後のいずれか早い方**で要求する。拒否された場合も他機能は制限しない（完了の伝達は Live Activity とフォアグラウンドのサウンドが担う） |
| FR-5.6.1 | 設定でリマインダーをオフにしている場合も、**許可要求は行う**。FR-2.13 の完了通知がリマインダーの設定とは独立して動作するため（FR-2.14.1）、許可自体は必要になる |
| FR-5.7 | FR-5.4（当日完了済みなら送らない）を満たすため、リマインダーは**日付を個別に指定した通知を60日分まとめて予約**する（TR-5）。`repeats: true` の繰り返し予約は使用しない |
| FR-5.8 | OSの通知許可状態（未決定 / 許可 / 拒否）ごとに、設定画面の表示と予約の挙動を次のとおりとする |
| FR-5.8.1 | **未決定**：設定画面は通常表示（オン・8:00）。ただし**60日分の予約は行わない**。FR-5.6 の契機で許可を取得した時点で予約する |
| FR-5.8.2 | **許可**：設定画面は通常表示。FR-5.7 に従って60日分を予約する |
| FR-5.8.3 | **拒否**：通知時刻とオン/オフの操作を**無効表示**にし、「iOSの設定で通知を許可してください」の一文と**設定アプリを開く導線**を表示する。予約は行わない。iOSではアプリから再要求できないため、この導線がなければ復帰手段がなくなる。FR-2.13 の完了通知もこの状態では送られない（FR-2.14.1） |
| FR-5.8.4 | 許可状態はアプリがフォアグラウンドに復帰するたびに再取得する。拒否から許可に変わっていた場合は、その時点で60日分を予約する |

> FR-5.3 の理由。習慣名を含めるとタスクリマインダーになり「やらなければ」という圧が生じる。残り件数を含めるとノルマ感が出る。「2分だけ」は行動のハードルを下げる文言であり、プロダクトの主張そのものである。
> FR-5.6 で許可要求をタイマー開始直前に置くのは、「2分後にお知らせします」という文脈が最も明確な瞬間だからである。初回起動時にまとめて要求すると用途が分からないまま拒否されやすい。習慣を登録したまま一度もタイマーを回さないユーザーを取りこぼさないよう、登録完了直後にも、通知をリマインダーと完了通知の2つに使うことを説明したうえで要求する経路を設ける（文言は TODO 1.7）。
> FR-5.1 に初期値を置かないと、設定画面に自ら足を運んだユーザー以外には通知が一切届かない。習慣化アプリでリマインダーが届かないのは機能欠落に等しい。
> FR-5.4.1 で0件時に予約を止めるのは、FR-5.3 により通知が習慣名も残り件数も含まないためである。習慣を全てアーカイブしたユーザーに「2分だけ」だけが届いても、何に対する通知か判断できない。

### FR-6: 設定

| ID     | 要件                                                                |
| ------ | ------------------------------------------------------------------- |
| FR-6.1 | 設定画面は「**ユーザー設定**」と「**習慣管理**」の2セクションで構成する。ユーザー設定の項目は「通知時刻」「通知のオン/オフ」「テーマ」の3つのみとし、これ以上増やさない。テーマは**ライト / ダーク / 端末に合わせる**の3択、**初期値は「端末に合わせる」**とする。アクセント色の変更は提供しない |
| FR-6.2 | サウンドのオン/オフは設定に持たず、端末のサイレントスイッチに委ねる |
| FR-6.3 | 設定画面の**習慣管理セクション**（FR-6.1）で、登録済み習慣に対して**並び替え・アーカイブ・習慣名の編集（FR-6.4）**の3操作を提供する。**削除と復元は提供しない**。アーカイブは一方通行とし、アーカイブすると3件の枠が空いて新しい習慣を登録できる。同じ内容を再開したい場合は新規登録する（履歴は分かれる） |
| FR-6.3.1 | アーカイブの実行前に**確認ダイアログを挟む**。確認文には「**元に戻せないこと**」と「**記録は残るがホーム画面には戻らないこと**」の2点を含める。Undo は提供しない |
| FR-6.4 | 習慣名の編集は再度ウィザードを経由させる。編集後も**同一の Habit として履歴と連続日数を引き継ぐ**             |
| FR-6.4.1 | 編集でウィザードを開く際、最初の自由入力欄に**現在の `title` をプリフィルする**。`originalIntent` は書き換えない（FR-1.8）。キャンセル時の挙動は FR-1.10.5 に従う |
| FR-6.4.2 | 編集フローが通る段階は次の順とする。**① `title` のプリフィル → ② FR-1.4.1 / FR-1.4.2 の文字数チェックと FR-1.5.1 の検出 → ③ FR-1.5.2 のソフト確認 → ④ 登録** |
| FR-6.4.2.1 | プリフィルした `title` が**現在の表示言語の上限を超えている場合**（端末言語の変更などで起こりうる。FR-1.4.3）も、編集画面は通常どおり開く。入力欄には**現在の文字数と上限を併記**し（例：45 / 30）、上限以内に収まるまで登録操作を無効にする。編集をやめる場合は FR-1.10 のキャンセルで元の `title` が保たれる（FR-1.10.5） |
| FR-6.4.3 | 編集フローでは、通常は **FR-1.3 の再分解ループ・FR-1.6 のテンプレート提示・FR-1.7 の汎用パターン提示を行わない**。すでに分解済みの文を対象とするため、これらの提示は不自然になる |
| FR-6.4.4 | ただし FR-1.5.1.3（目標表現の語尾を検出）に該当した場合は **FR-1.3 の再分解に入る**。この再分解は FR-1.3.1 の回数上限に算入する |
| FR-6.4.5 | 編集フローで FR-1.3.1 の上限（3回目のNo）に到達した場合は、**例外的に FR-1.7 の汎用パターン3種を提示する**。上限到達は「自力で分解できていない」状態であり、新規登録と同じ救済を与える。FR-6.4.3 が汎用パターンを出さないのは分解済みの文を扱っている間のみで、再分解に入った後は対象が目標表現に戻っているため適用しない |

> FR-6.3 から削除を外したのは、`deleteRule: .cascade` により過去の Session が消え、FR-3.9 の通算完了回数と最長連続日数が遡って書き換わるためである。統計値を永続化せず Session から算出する設計（§6）と、「論理削除を採用し履歴を失わせない」という方針の両方に反する。アーカイブでホームから消え枠も空くため、ユーザーから見た体験は削除とほぼ変わらない。
> FR-6.3.1 で確認ダイアログを挟むのは、復元を廃止した結果アーカイブが**アプリ唯一の取り消し不能な操作**になったためである。FR-2.5 がタイマーの中断に確認を挟まないのは「2分を止める」判断の速さを優先しているからであり、設定画面内の不可逆操作とは文脈が異なる。Undo を置かないのは、`archivedAt` を戻す経路を作ると「一方通行」という共通規則に例外が生まれ、ヒートマップの分母が事後的に変化する余地が復活するためである。
> **復元も同じ理由で外した。** `archivedAt` を nil に戻すと、FR-3.8.1 の分母（その日に有効だった習慣数）が `createdAt` と `archivedAt` から算出される仕様上、アーカイブ期間中の過去日も分母に算入され、**表示済みのヒートマップの濃淡が事後的に薄くなる**。これを避けるにはアーカイブ期間の履歴を保持する別モデルが必要になり、分母算出ロジックとテストが複雑化する。アーカイブを一方通行にすれば `archivedAt` は一度立ったら変わらず、分母が過去に遡って変化する経路自体がなくなる。
> FR-6.4.3 で編集時にテンプレートと汎用パターンを出さないのは、これらが「まだ分解されていない目標」を分解するための道具だからである。編集の対象は既に分解を通過した `title` であり、そこにテンプレートを提示すると分解し直しを促すことになる。一方で、編集で目標表現に書き換えられた場合（「読書を続ける」に変更した等）は分解が必要になるため、FR-6.4.4 で再分解の経路を残す。
> FR-6.4.5 を設けたのは、FR-6.4.3（汎用パターンを出さない）と FR-1.3.1（3回目のNoで汎用パターンへ強制誘導）が編集フローで衝突し、**遷移先のない行き止まり**が生じていたためである。上限到達時に限って汎用パターンを解禁することで、新規登録フローと同じ着地点に収束させる。
> FR-6.4 は「腕立て1回」を「本を1ページ読む」に書き換えても連続日数が引き継がれる抜け穴を持つ。編集は表現の微調整を想定した機能であり、内容を変える場合はアーカイブと新規登録に進むのが本来の経路である。この抜け穴は誤字修正で積み上げが消える事故を避けることを優先し、受け入れる。

## 6. データモデル（SwiftData）

```swift
@Model final class Habit {
    var id: UUID
    var title: String           // 分解後の2分アクション。上限は登録時の表示言語に依存（FR-1.4.1）。保存後に上限を超えても無効化しない（FR-1.4.3）
    var originalIntent: String  // 分解前の入力
    var createdAt: Date
    var order: Int              // アクティブな習慣内での表示順
    var archivedAt: Date?
    @Relationship(deleteRule: .cascade) var sessions: [Session]
}

@Model final class Session {
    var id: UUID
    var startedAt: Date         // 集計上の日付帰属はこちら（FR-3.10）
    var completedAt: Date       // 完了したSessionのみ保存するためOptionalではない
    var habit: Habit?
}
```

### 設計方針

- **完了した Session のみを永続化する**（FR-3.3）。中断されたセッションは保存しないため、`completedAt` は非Optional
- `elapsedSeconds` は保持しない。完了 Session の経過時間は常に120秒であり、冗長なため
- **連続日数・最長連続日数・通算完了回数・ヒートマップの達成率は永続化しない**。Session群からの算出とする（テスト対象にするため）
- 集計の日付キーは `startedAt` のローカル日付とする。`completedAt` は使わない（FR-3.10）
- ヒートマップの分母（その日に有効だった習慣数）は Habit の `createdAt` と `archivedAt` から算出する
- 論理削除（`archivedAt`）を採用し、履歴を失わせない。アーカイブ済み Habit は FR-1.9 の3件制限には数えないが、過去の Session と分母の算出には引き続き使用する
- 習慣名の編集は同一 Habit の `title` を書き換えるだけとし、Session との関連は維持する（FR-6.4）
- `order` は**アクティブな習慣内での表示順**であり、アーカイブ時に無効化してアクティブな習慣を0から連番で再採番する。アーカイブ済み Habit の `order` は参照しない
- `archivedAt` は**一度設定したら変更しない**（FR-6.3 で復元を提供しないため）。これによりヒートマップの分母が過去に遡って変化しないことが保証される
- 物理削除を行わないため `deleteRule` が発動する経路は存在しない。`.cascade` の指定は残すが、v1.0 では到達しない

## 7. 技術要件

| 領域           | 採用          |
| -------------- | ------------- |
| UI             | SwiftUI       |
| アーキテクチャ | MVVM          |
| 状態管理       | `@Observable` |
| 永続化         | SwiftData     |
| 非同期         | async/await   |
| テスト         | Swift Testing |
| 最低OS         | iOS 26.0      |

### 実装上の必須事項

**TR-1: 経過時間の算出**
`Timer` の tick を積算する実装は禁止する。バックグラウンド移行・端末スリープ・時刻変更で破綻するため、**経過時間は常に `startedAt` と現在時刻の差分から算出**し、`Timer` は再描画トリガーとしてのみ使用する。

**TR-2: TimerEngine の分離**
タイマーロジックは SwiftUI / SwiftData に依存しない純粋な型として実装し、時刻取得を `Clock` プロトコルで注入可能にする。これにより2分経過・バックグラウンド復帰・日跨ぎをすべてユニットテストで検証できる状態にする。

**TR-3: Repository 層**
`@Query` を View に直書きしない。`ModelContext` へのアクセスは Repository を経由させ、ViewModel には Repository をイニシャライザ注入する。ViewModel を SwiftData 非依存でテストできる状態を保つ。

**TR-4: ネットワーク通信を行わない**
完全オフライン動作とする。App Privacy では「データを収集しない」を宣言する。iCloud同期を対象外としたため（§3 / §10）、これは v1.0 限定ではなく**継続する方針**である。

**TR-5: リマインダー通知は日付指定で60日分を予約する**
ローカル通知は**予約時にしか条件を判定できない**ため、`UNCalendarNotificationTrigger` を `repeats: true` で予約すると FR-5.4（当日完了済みなら送らない）が実装できない。`UNNotificationServiceExtension` はリモート通知専用でローカル通知には適用されない。

したがって次の方式をとる。

- 日付を個別に指定した通知を**60日分予約する**
- その日の全習慣が完了した時点で、**当日分の予約をキャンセルする**
- アプリ起動時に残り予約数を確認し、60日分に**補充する**
- 通知時刻の変更・リマインダーのオフ時は、**リマインダー分の予約のみを破棄して組み直す**
- **登録済み習慣が0件になった時点で、リマインダーの全予約をキャンセルする**（FR-5.4.1）。習慣が1件でも登録された時点で60日分を予約し直す

**予約日数を60日とした理由。** iOSの保留通知上限は64件で、FR-2.13 の完了通知がタイマー実行中に1件を占有する。63日分まで取れるが、v1.1 で通知を追加した際に予約が失敗するのを避けるため4件の余裕を残して60日とした。

**通知の識別子で種別を区別する。** リマインダーと FR-2.13 の完了通知は目的も生存期間も異なるため、identifier に接頭辞を付けて分離する。

| 種別                       | identifier の接頭辞 | 破棄の契機                                       |
| -------------------------- | ------------------- | ------------------------------------------------ |
| リマインダー（FR-5.1）     | `reminder.`         | 通知時刻の変更、リマインダーのオフ、当日分の完了 |
| 完了通知（FR-2.13）        | `timer.`            | フォアグラウンドでの完了、タイマーの中断         |

**`removeAllPendingNotificationRequests()` は使用しない。** リマインダーのオフ操作で実行中タイマーの完了通知まで消えると、FR-2.14.1（完了通知はリマインダー設定に依存しない）に反する。破棄は常に接頭辞で絞り込んだ identifier 指定で行う。

**既知の制約：60日を超えてアプリを起動しなかった場合、リマインダーは停止する。** 補充の契機がアプリ起動しかないためである。これは FR-5.4（当日完了済みなら送らない）を満たすために `repeats: true` を捨てた結果として方式上避けられない。習慣化アプリでは離れたユーザーへのリマインダーが復帰の導線になりうるが、当日完了済みでも通知が届く状態の方が体験として悪いと判断し、この制約を受け入れる。

予約・キャンセル・補充のロジックは `UNUserNotificationCenter` に依存しない純粋な型として実装し、テスト可能にする。

## 10. 参考

### Deployment Target を iOS 26 とした理由

- **iOS 16 を除外**: `@Observable` と SwiftData がいずれも iOS 17+。16対応は `ObservableObject` + Core Data への退行を意味し、技術要件と両立しない
- **iOS 17 を除外**: SwiftData のマイグレーションと `#Predicate` に実用上の制約があり、17専用の回避コードが必要になる。リリース時点で3世代前であり保守コストに見合わない
- **iOS 18 を除外**: iOS 26 SDK でビルドすれば新デザインは自動適用され、下位OSでは従来表現にフォールバックするため、全画面に `#available` 分岐が必要になるわけではない。除外の理由は**新デザインの細部をSDK任せにせず作り込むため**であり、下位OSでの見え方を検証するコストと、新デザイン固有APIを使う箇所で分岐が生じることを避けることを優先した。本アプリは画面数が少なくデザインそのものが製品価値の中核であるため、この判断の重みが大きい
- 将来的な Foundation Models framework の導入が iOS 26+ を前提とするため、ターゲットの再引き上げが不要になる

### iCloud同期を対象外とした理由

- **機種変更は端末のiCloudバックアップで守られる。** SwiftData のストアは Application Support 配下に置かれ、`isExcludedFromBackup` を指定しない限りバックアップに含まれる。新端末をバックアップから復元すれば習慣・連続日数・履歴はそのまま戻るため、同期で解決したい最大の用途はOS標準の機能で満たされる
- **iPhone専用アプリであり、複数端末で同時に使う前提がない**（§0 プラットフォーム）
- **CloudKit を入れるとデータモデルに制約が生じる。** SwiftData + CloudKit は全プロパティをOptionalまたはデフォルト値付きにすることを要求するため、§6 で「完了した Session のみ保存するため非Optional」と決めた `completedAt` を崩す必要がある。同期を採らないことでこの制約から解放される
- **TR-4（ネットワーク通信を行わない）と NFR-3（外部へのデータ送信を一切行わない）を v1.0 以降も維持できる**

失われるのは「アプリを削除して入れ直した場合の復元」のみ（バックアップ復元は端末単位で、アプリ単体の再インストールには効かない）。登録上限3件のアプリでは許容できる範囲と判断した。

### 制作フロー（想定）

1. SwiftUI で動くプロトタイプを先行実装（Claude Code 併用）
2. シミュレータのキャプチャを Figma に取り込みデザインを整える
3. 確定したデザイントークンを SwiftUI に反映
4. ストア用スクリーンショットは `ParthJadhav/app-store-screenshots`（別リポジトリ、Next.js製エディタを scaffold）で作成。キャプチャ元は6.1インチシミュレータを推奨
